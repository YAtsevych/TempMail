==========================================================================
ІНСТРУКЦІЯ З ТЕСТУВАННЯ СИСТЕМИ ОБРОБКИ ДАНИХ (STRESS TESTING GUIDE)
==========================================================================

Цей документ описує процедуру проведення нагрузочного тестування 
анонімної системи електронних комунікацій, а також сценарії перевірки 
алгоритмів фільтрації трафіку та інтелектуального управління чергами.

--------------------------------------------------------------------------
1. ПІДГОТОВКА ТА БАЗОВІ КОМАНДИ ДЛЯ ЗАПУСКУ
--------------------------------------------------------------------------

Для повноцінного тестування компоненти бекенду запускаються в окремих 
терміналах із директорії `./backend`.

* Крок 1: Запуск API-сервера
  Команда: 
   npx nodemon --exec ts-node src/index.ts
  Призначення: Прийом вхідного трафіку, первинна валідація та маршрутизація.

* Крок 2: Запуск фонового обробника (Worker)
  Команда:  
  npm run worker:dev
  Призначення: Обробка черг із використанням алгоритму WFQ (Weighted Fair Queueing).

* Крок 3: Запуск скрипта нагрузочного тестування
  Команда: 
   node test/queue-stress-test.js
  Призначення: Генерація синтетичного високонавантаженого потоку листів (10 000 запитів).

--------------------------------------------------------------------------
2. СЦЕНАРІЇ ТЕСТУВАННЯ (TEST CASES)
--------------------------------------------------------------------------

ВАРІАНТ 1: Тестування алгоритму планування черг WFQ (Миттєве навантаження)
--------------------------------------------------------------------------
Мета: Дослідити поведінку системи в умовах лавиноподібного трафіку та 
перевірити пріоритетність обробки критичних повідомлень перед фоновими.

Порядок дій:
  1. Запустити API-сервер.
  2. Запустити скрипт генерації тестів (node test/queue-stress-test.js).
     У чергу МИТТЄВО направляється масив із 10 000 запитів (за винятком 
     трафіку, який одразу блокується вбудованим захистом від DDoS на рівні API).
  3. Тільки після цього запустити воркер (npm run worker:dev).

Що перевіряється:
  Візуалізується робота алгоритму зважених дефіцитних черг (WFQ). 
  Транзакційний високопріоритетний трафік (Mice/OTP) обробляється та 
  зберігається в базу даних першочергово безперервним потоком, тоді як 
  маркетинговий трафік (Elephant) очікує на вивільнення квантів часу.

ВАРІАНТ 2: Тестування пропускної здатності та фільтрації (Потокове навантаження)
--------------------------------------------------------------------------
Мета: Аналіз стабільності сервера при обробці розподіленого в часі 
потоку даних та перевірка роботи ешелонованого захисту.

Порядок дій:
  1. Запустити API-сервер.
  2. Запустить фоновий воркер (npm run worker:dev).
  3. Запустити скрипт генерації тестів (node test/queue-stress-test.js).

Що перевіряється:
  Скрипт імітує реальний інтенсивний трафік — 10 000 листів надходять 
  пачками (батчами) з контрольованим інтервалом. Тестується здатність 
  сервера паралельно приймати, фільтрувати та розподіляти завдання без збоїв. 
  Після завершення тесту в термінал виводиться зведена таблиця метрик.

--------------------------------------------------------------------------
3. ІНТЕРПРЕТАЦІЯ МЕТРИК ФІНАЛЬНОГО ЗВІТУ
--------------------------------------------------------------------------

Після завершення Варіанту 2 в консоль виводиться "ФІНАЛЬНИЙ ЗВІТ ПРОДУКТИВНОСТІ". 
Нижче наведено опис ключових метрик, що перевіряються:

* Total Input (Усього надійшло в систему): 
  Загальна кількість успішно прийнятих та поміщених у чергу запитів. 
  Різниця між 10 000 та цим числом показує обсяг відсіченого DDoS-фільтром трафіку.

* MICE / OTP (Пропущено транзакційних листів):
  Кількість верифікованих критично важливих повідомлень (пакети малого розміру, 
  але високого пріоритету), що оброблені поза чергою FIFO.

* ELEPHANT (Пропущено маркетингових листів):
  Кількість фонового трафіку (великі пакети, що не потребують миттєвої доставки), 
  обробленого системою в моменти зниження інтенсивності OTP.

* MIME Фільтр / .exe (Відсічено 3-м ешелоном):
  Кількість листів, заблокованих вбудованим контент-фільтром безпеки 
  через виявлення заборонених вкладень або небезпечних сигнатур (RULE_5).

* Avg Mice (Середній час обробки критичних OTP):
  Ключовий показник затримки (Latency) для пріоритетних завдань. Статус 
  "Soft Real-Time" підтверджує, що задержка перебуває в межах допустимої норми.

* p99 Latency (Перцентиль швидкодії):
  Показує максимальний час обробки для 99% усіх запитів. Дозволяє виявити 
  "хвости затримок" (long-tail latency) під максимальним навантаженням.
==========================================================================
